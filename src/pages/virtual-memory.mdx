{/* 4. EXPLANATION / DEEP DIVE */}
<section class="ml-section animate-fade-up" id="deep-dive">
  <div class="ml-section-header">
    <span class="ml-section-label">Problems elaborated</span>
    <h2 class="ml-section-title">Why Direct Access Failed</h2>
    <p class="ml-section-subtitle">
      Early operating systems let programs directly access physical RAM. This caused three massive problems.
    </p>
  </div>

  <div class="ml-prose">
    <h3>Problem 1: The Wild West (Security)</h3>
    <p>
      In early operating systems, there was no memory protection. Some programs could accidentally (or maliciously) write data into another program's memory space. This would instantly cause your computer to crash with a Blue Screen of Death. 
    </p>
    <p>
      <strong>The Fix:</strong> Virtual Memory gives each program its own isolated "Virtual Space." The OS divides this virtual space into fixed-size chunks called <strong>Pages</strong>, and divides Physical RAM into matching chunks called <strong>Frames</strong>. The OS's job is to securely map these Virtual Pages into any available Physical Frames. Because the OS handles this translation behind the scenes, a program literally has no way to even guess the physical address of another program, completely fixing the security hole!
    </p>
    <SecurityVisualizer client:load />
    
    <br/>
    <h3>Problem 2: Insufficient Memory (Demand Paging & Swap)</h3>
    <p>
      Modern computers need a lot of memory. If you only have 8GB of RAM but try to open 10GB worth of programs, an old OS would simply throw an "Out of Memory" error.
    </p>
    <p>
      <strong>The Fix:</strong> The OS uses a <strong>Swap File</strong> on your Hard Disk. When RAM is completely full, the OS takes idle programs and "swaps" them to the disk. When you need them again, it swaps them back into RAM. This is called <em>Demand Paging</em>. It makes your memory feel infinite (though it costs some speed).
    </p>
    <SwapVisualizer client:load />

    <br/>
    <h3>Problem 3: Wasted Memory (Shared Pages)</h3>
    <p>
      Imagine you have 4 programs running, and they all need to use the Standard C Library (libc) to do basic math. In an old OS, that library gets loaded into RAM 4 separate times, wasting huge amounts of space.
    </p>
    <p>
      <strong>The Fix:</strong> Because the OS translates Virtual addresses to Physical ones, it can point the virtual memory of all 4 programs to the <em>exact same physical copy</em> of the library in RAM. We call this <strong>Shared Pages</strong>.
    </p>
    <SharedLibraryVisualizer client:load />

  </div>
</section>

{/* 5. DEEP DIVE: HOW IT WORKS */}
<section class="ml-section animate-fade-up" id="how-it-works">
  <div class="ml-section-header">
    <span class="ml-section-label">Deep Dive</span>
    <h2 class="ml-section-title">How It All Works Under the Hood</h2>
    <p class="ml-section-subtitle">
      A breakdown of the hardware and software mechanisms that make virtual memory possible.
    </p>
  </div>

  <div class="ml-prose">
    
    <h3>1. The Core Concept: Pages & Frames</h3>
    <p>
      As we saw earlier, virtual memory solves <strong>External Fragmentation</strong> by breaking the virtual address space into uniform chunks called <strong>Pages</strong>, and physical RAM into matching chunks called <strong>Frames</strong> (typically 4 KB each). 
      Because they are exactly the same size, any virtual page can fit into any available physical frame, no matter how scattered the free space in RAM gets.
    </p>

    <h3>2. The Directory: Page Tables</h3>
    <p>
      The OS keeps track of these mappings using a data structure called a <strong>Page Table</strong>. You can think of a Page Table like a massive "library of old phonebooks." Every single running process gets its own personal phonebook. Whenever the OS switches from one program to another (a Context Switch), it updates a hardware pointer called the <strong>Page Table Base Register (PTBR)</strong> to point to the current program's phonebook.
    </p>
    <p>
      These tables don't just hold physical frame numbers. Each entry is packed with extra data:
    </p>
    <ul>
      <li><strong>Protection Bits:</strong> Define permissions like <em>Read-Only</em>, <em>User/Supervisor</em> (restricting access to the OS), and <em>No Execute</em> to stop malicious software from running injected code.</li>
      <li><strong>Status Bits:</strong> Let the hardware know the state of the page. The <em>Valid</em> bit tells us if the frame is actually in RAM. The <em>Dirty/Modified</em> bit tracks if the data has been changed and needs saving to the disk later. The <em>Accessed</em> bit tracks recent usage, and the <em>Global</em> bit marks pages shared across all processes (like the OS kernel).</li>
    </ul>
    <div class="ml-analogy">
      <strong>The Two-Access Problem:</strong> Page tables are so huge they have to be stored in physical RAM. If the CPU has to read the page table from RAM <em>every single time</em> it wants to access memory, it doubles the access time! We need a hardware solution.
    </div>
    
    <br/>
    <ContextSwitchVisualizer client:load />
    <br/>
    <br/>
    <PageTableEntryVisualizer client:load />

    <h3>3. The Hardware Hero: The MMU</h3>
    <p>
      Enter the <strong>Memory Management Unit (MMU)</strong>. Integrated directly into the processor chip, the MMU acts as the "Sheriff in Town." It manages all memory requests, translates addresses instantly, and strictly enforces those protection bits to catch malicious processes trying to interfere with others.
    </p>
    <p>
      When the CPU asks for data, the MMU splits the virtual address into two parts: a <strong>Virtual Page Number</strong> and a <strong>Page Offset</strong>. For a standard 4KB page, the last 12 bits of the address are the Offset. The MMU only translates the Page Number into a Frame Number; the Offset (the exact location of the byte within the page) stays exactly the same!
    </p>

    <AddressSignalPipeline client:load />
    <br/>
    <br/>

    <h3>4. The VIP Fast-Pass: The TLB</h3>
    <p>
      To solve the slow Two-Access Problem, the MMU contains a tiny, ultra-fast hardware cache called the <strong>Translation Lookaside Buffer (TLB)</strong>. If the Page Table in RAM is a massive city library of phonebooks, the TLB is like a small coffee shop next door that only remembers the numbers of the people you call the most. Modern systems actually use two: an <em>Instruction TLB</em> and a <em>Data TLB</em>.
    </p>
    <p>
      To keep things fast during a Context Switch, the TLB uses an <strong>Address Space Identifier (ASID)</strong>. This acts like a nametag for each translation, allowing the TLB to store entries for multiple programs at the same time without needing to be flushed and repopulated every time you switch apps!
    </p>

    <h3>5. Interactive TLB Simulator</h3>
    <p>
      Try acting as the MMU yourself! Select a virtual page to request below. See if you get a fast <strong>TLB Hit</strong>, a slower <strong>TLB Miss</strong> (where the MMU has to walk to the Page Table in RAM), or a <strong>Page Fault</strong>. Watch how the TLB automatically evicts old entries to make room for new ones.
    </p>

    <TlbSimulator client:load />
    <br/>
    <br/>

    <h3>6. The Emergency: Page Faults & Traps</h3>
    <p>
      What happens if the MMU checks the Page Table and the "Valid" bit says the page isn't even in RAM? The MMU throws a hardware exception called a <strong>Trap</strong> (specifically a Page Fault). 
    </p>
    <p>
      The OS immediately takes over and checks for a <strong>Segmentation Fault</strong> (did the program try to access memory it never even owned?). If it was a valid request but the page was just swapped to the hard disk, the OS pauses the program, finds a free frame, loads the missing page from the disk, updates the page table, and copies the entry into the TLB using an eviction policy like <em>Least Recently Used (LRU)</em> or <em>Round Robin</em>. Then, the program resumes!
    </p>

    <h3>7. The Big Picture: Real-Time Memory Mapping</h3>
    <p>
      Now that you understand Pages, Frames, the MMU, and swapping, you can visualize how all these pieces fit together. The 3D matrix below represents a physical RAM cube, showing how Code pages, Heap frames, Shared Libraries, and swapped Disk sectors all co-exist in non-contiguous hardware blocks simultaneously.
    </p>

    <PageFrame3DVisualizer client:load />
    <br/>

  </div>
